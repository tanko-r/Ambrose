# Phase 8.1: Documentation Sync + Verification - Research

**Researched:** 2026-02-13
**Domain:** Documentation verification, tracking document updates, human feature verification
**Confidence:** HIGH

## Summary

Phase 8.1 is a documentation and verification phase, not a code implementation phase. The v1.0 milestone audit (2026-02-14) identified three categories of tech debt: (1) unverified features that were built but never marked complete (TRANS-01..04, NEW-01..04), (2) stale tracking documents (ROADMAP.md, REQUIREMENTS.md, STATE.md) with incorrect checkboxes and status percentages, and (3) missing VERIFICATION.md files for phases 5, 6, and 7.

All eight requirements in question (TRANS-01..04, NEW-01..04) have corresponding code committed to the codebase. The transmittal dialog (`transmittal-dialog.tsx`), new project dialog (`new-project-dialog.tsx`), delete project dialog (`delete-project-dialog.tsx`), and backend endpoints (`/api/transmittal/<id>`, `/api/session/<id>/save`, `DELETE /api/session/<id>`) all exist and were confirmed in the 06-03-SUMMARY.md. However, no human has verified these features actually work in the browser. The phase 6 plan 03 included a human verification task (Task 3) that was never completed.

**Primary recommendation:** Structure this phase as two types of work: (1) human verification tasks requiring the user to test features in the browser and confirm they work, and (2) automated documentation updates that fix tracking documents based on verification results.

## Common Pitfalls

### Pitfall 1: Marking Requirements Complete Without Human Verification
**What goes wrong:** Requirements are marked [x] based on code existence alone, but the feature may not actually work end-to-end in the browser.
**Why it happens:** The audit already confirmed code exists, so it's tempting to skip verification.
**How to avoid:** TRANS-01..04 and NEW-01..04 must be human-tested in the browser before marking complete. Phase 8.1 success criteria #1 and #2 explicitly require human verification.
**Warning signs:** Any plan that marks requirements complete without a human verification checkpoint.

### Pitfall 2: Updating STATE.md Progress Without Counting Plans
**What goes wrong:** Progress percentages are estimated rather than calculated from actual plan execution.
**Why it happens:** Plans may have been executed out of order or via quick tasks.
**How to avoid:** Count executed plans from SUMMARY files. Phase 5: 3/3 plans have SUMMARYs. Phase 6: 5/5 plans have SUMMARYs. Phase 7: 4/5 plans have SUMMARYs (plan 05 never executed).
**Warning signs:** Any percentage not derived from SUMMARY file counts.

### Pitfall 3: Forgetting ROADMAP.md Has Two Stale Sections
**What goes wrong:** Only the plan checkboxes are updated but the Progress table at the bottom is not, or vice versa.
**Why it happens:** ROADMAP.md has plan checkboxes in the phase detail sections AND a summary Progress table near the bottom. Both need updating.
**How to avoid:** Update both: (1) individual plan checkboxes inside `<details>` blocks and (2) the Progress table.

### Pitfall 4: Phase 7 is NOT 100% Complete
**What goes wrong:** Phase 7 gets marked as complete/100% when plan 07-05 was never executed.
**Why it happens:** Plans 07-01 through 07-04 were all executed, and quick task 6 fixed Critical/High QA items.
**How to avoid:** Phase 7 should be marked 4/5 plans executed. The verification checkpoint (07-05) was partially addressed by QA testing but was never formally completed. STATE.md should reflect this nuance.
**Warning signs:** Marking Phase 7 at 100% or "Complete" without noting the unexecuted plan.

### Pitfall 5: Stale REQUIREMENTS.md Traceability Table
**What goes wrong:** The checkbox area is updated but the traceability table at the bottom still shows "In Progress."
**Why it happens:** The traceability table is a separate section that's easy to miss.
**How to avoid:** Update both the checkbox list AND the traceability table when marking requirements complete.

## Dependency Analysis

### What Must Happen Before Documentation Updates

```
Human verification of TRANS-01..04 (browser test)
  |
  v
Human verification of NEW-01..04 (browser test)
  |
  v
Mark REQUIREMENTS.md checkboxes (depends on verification passing)
  |
  v
Update ROADMAP.md checkboxes + progress table
  |
  v
Update STATE.md progress + status
  |
  v
Create VERIFICATION.md files for phases 5, 6, 7
```

**Critical dependency:** REQUIREMENTS.md updates MUST NOT happen until human verification confirms features work. If transmittal or new project features have bugs, those need fixing before marking complete.

### VERIFICATION.md Can Be Created in Parallel

The VERIFICATION.md files for phases 5, 6, and 7 can be created based on existing SUMMARY files and code inspection. They document what was already built and verified by the automated verifier. These do NOT depend on the TRANS/NEW human verification.

## Plan Structure Recommendation

The planner should consider splitting this into two types of plans:

1. **Human verification plan:** A checkpoint plan with detailed steps for the user to test transmittal and new project features in the browser. This is blocking -- if features don't work, they need fixing.

2. **Documentation update plan:** An automated plan that updates all tracking documents and creates VERIFICATION.md files. This can execute after verification passes.

This separation keeps the blocking dependency (human testing) from holding up the non-blocking work (doc updates for already-verified phases like 5, 6, 7).
