<objective>
Make analysis non-blocking: the start endpoint returns immediately with a job ID, analysis runs in a background thread, and the frontend polls for progress.

Purpose: Railway has a hard 5-minute HTTP timeout. The current GET /api/analysis/{session_id} endpoint blocks for 5-30 minutes while analysis runs, which will be killed on Railway. This plan converts to an async POST+poll pattern using Python's built-in threading module.

Output: New POST /start endpoint, background thread execution, updated frontend hook — analysis no longer holds an HTTP connection open.
</objective>

   - If `session.get('analysis')` already exists, return `{"status": "already_complete", "session_id": session_id}` with HTTP 200
   - Check if a job is already running for this session (iterate `_analysis_jobs` for matching session_id with status='running'). If so, return the existing job_id with HTTP 200.

     g. Sets job status to 'complete'
     h. On exception: calls `clear_progress()`, sets job status to 'failed' with error message
   - Spawn `threading.Thread(target=_run_analysis, args=(app, session_id, job_id), daemon=True).start()`

3. **Create `GET /api/analysis/jobs/<job_id>`** endpoint:

**CRITICAL THREAD SAFETY:** The `_run_analysis` function accesses the `sessions` dict and calls `save_session()`. The existing `sessions` dict is not explicitly thread-safe, but Python's GIL provides adequate protection for dict reads/writes at this concurrency level (single analysis thread + request threads). The `_analysis_jobs` dict uses an explicit lock since it's accessed from multiple threads concurrently.

**CRITICAL APP CONTEXT:** Use `current_app._get_current_object()` before spawning — the `current_app` proxy is thread-local and will not work in the background thread.

1. **frontend/src/lib/api.ts** — Add a new `startAnalysisJob()` function:
   ```typescript
   export async function startAnalysisJob(sessionId: string): Promise<{
     job_id?: string;
     status: string;
     session_id: string;
   }> {
     return request(`/api/analysis/${sessionId}/start`, { method: 'POST' });
   }
   ```
   Keep the existing `getAnalysis()` function — it's still used to fetch completed analysis results.

2. **frontend/src/hooks/use-analysis.ts** — Rewrite the `startAnalysis` callback to use the non-blocking pattern:

   **Current pattern (BLOCKING):**
   - Calls `getAnalysis(sessionId)` which blocks for 5-30 minutes
   - Polls progress in parallel via setInterval

   **New pattern (NON-BLOCKING):**
   - Calls `startAnalysisJob(sessionId)` which returns immediately with HTTP 202
   - If response.status === 'already_complete', fetch full results via `getAnalysis(sessionId)` and hydrate store
   - Otherwise, start polling. The polling loop already works — it calls `getAnalysisProgress()` every 1 second
   - When polling detects `status === 'complete'`, fetch full results via `getAnalysis(sessionId)` and hydrate the store
   - Remove the long-running `getAnalysis()` call from the main flow — it should only be called AFTER completion is detected

   Specifically, the `startAnalysis` callback should:
   ```
   a. Call startAnalysisJob(sessionId)
   b. If already_complete: fetch via getAnalysis(), hydrate store, done
   c. Else: set analysisStatus to 'analyzing', start polling
   d. In the polling callback, when status === 'complete':
      - Stop polling
      - Fetch full results via getAnalysis(sessionId)
      - Hydrate store with setAnalysis()
      - Set completedRef.current = true
      - toast.success("Analysis complete")
   e. Error handling: if startAnalysisJob fails, show error toast and reset state
   ```

   The key change is moving the `getAnalysis()` call from "blocking fire-and-forget" to "called only after polling detects completion".

3. **Import the new `startAnalysisJob`** in use-analysis.ts:
   ```typescript
   import { getAnalysis, getAnalysisProgress, startAnalysisJob } from "@/lib/api";
   ```

**IMPORTANT:** The existing `startPolling` callback and its incremental risk handling logic should remain UNCHANGED. The only changes are:
- How analysis is initiated (POST instead of blocking GET)
- When full results are fetched (after polling detects completion, not as a blocking call)
